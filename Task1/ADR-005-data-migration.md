# ADR-005. Миграция данных

## Контекст

Домены и Celery-задачи используют общую PostgreSQL, включая прямое чтение чужих таблиц. Большой объем данных нельзя переносить целиком при остановленной платформе.

## Требования

Перенести данные каждого сервиса с сохранением идентификаторов и подтвержденных операций, минимизировать простой, предусмотреть сверку и откат. Не создавать двух независимых владельцев записи одной сущности.

## Решение

Поток переноса показан на [отдельной схеме миграции](data-migration.puml). На [основной C2](C2-to-be.puml) показаны сервисы и совместимость API без технических деталей CDC.

### Общая процедура

1. **Подготовка.** Найти таблицы, читателей, писателей, фоновые задачи и внешние callbacks домена. Назначить целевого владельца, подготовить схему и преобразования. Проверить резервную копию и восстановление. Удаление старых полей откладывается до конца перехода.
2. **Снимок и CDC.** До начала копирования зафиксировать согласованный снимок PostgreSQL и связанную с ним позицию WAL. Debezium сохраняет изменения в отдельных миграционных топиках Kafka. CDC не подменяет доменные события и не должен запускать платежи или уведомления.
3. **Загрузка порциями.** Копировать историю по диапазонам ключей и дат с контрольными точками и ограничением скорости. Сначала загрузить нужные для работы данные. Изменения после позиции снимка применить в порядке версий, включая удаления. Повтор порции безопасен, старая запись не перезаписывает более новую.
4. **Сверка.** Сравнивать данные на одной контрольной позиции: число записей, ключи, нормализованные контрольные суммы и бизнес-инварианты. Параллельно читать данные из старой и новой системы и сравнивать ответы, возвращая пользователю только ответ действующей системы. Мониторить задержку CDC, ошибки переноса, рост WAL и нагрузку исходной БД.
5. **Передача записи.** Для выбранной группы кратко закрыть старую запись, включая воркеры и административные операции. Дождаться завершения текущих транзакций, применить CDC до конечной позиции и повторить сверку. Отключить прямой CDC для переданной группы, запретить старому владельцу запись, переключить чтение и запись на сервис. При превышении согласованного окна отменить переключение до открытия новой записи.
6. **Стабилизация.** Проверить новые операции и метрики, сохранить старые данные только для чтения и отката. Новые изменения фиксируются в журнале переноса или outbox. После контрольного периода, завершения старых процессов и проверки отсутствия обращений архивировать либо удалить старые таблицы по правилам хранения.

Для заказов и денежных операций предпочтителен перенос по жизненному циклу: новые сущности создаются в сервисе, старые завершаются в монолите. Владелец определяется по сохраненному идентификатору, а не по текущему проценту трафика. Общие изменяемые данные, например баланс водителя, передаются целиком для выбранной группы, без двух расчетчиков баланса.

### Особенности сервисов

| Сервис | Что переносим | Переключение и проверка |
| --- | --- | --- |
| Notification | Устройства, шаблоны, настройки, ожидающие задания и журнал доставки | Дождаться завершения выполняемых задач, передать ожидающие с прежними ID и отключить старых отправителей. История не запускает повторную отправку. При неопределенном результате push возможен дубль, если провайдер не поддерживает идемпотентность |
| Geography | Геозоны, настройки провайдеров, актуальные координаты, геоиндекс | Справочники переносятся снимком и CDC. Индекс строится заново, текущие координаты поступают из рабочего потока с проверкой времени и свежести. Redis не копируется как источник истории. Проверяем полноту зон и актуальность поиска |
| Driver | Профили, автомобили, смены, доступность, активные резервы | Перенос по группам водителей, резерв и доступность передаются вместе. Все пути назначения, включая монолит, обращаются к единому владельцу. Проверяем отсутствие двух активных резервов одного водителя |
| Pricing | Правила, версии тарифов, действующие котировки | Сравниваем расчет на одинаковых входных данных и версиях правил. Кеш прогревается, динамические коэффициенты восстанавливаются из потока. Принятые котировки сохраняют цену и срок действия |
| Fraud | Правила, версии моделей, результаты проверок, необходимые исторические признаки | Сначала проверочный расчет риска и сравнение решений без влияния на операции, затем переключение обязательных проверок. Историю загружаем из исходных данных, не предполагая, что Kafka содержит ее целиком |
| Payments | Платежи, возвраты, корпоративные счета и реквизиты, токены провайдеров, внешние ID и ключи идемпотентности | Новые операции идут в собственную БД Payments, старые завершаются у прежнего владельца. Callbacks маршрутизируются по ID операции. Полная сверка сумм, валют, статусов и внешних выписок |
| Payouts | Реестр начислений, балансы и банковские реквизиты водителей, выплаты и банковские ID | Перенос в собственную БД Payouts по счетам водителей после завершения либо согласованной передачи незавершенных выплат. На время передачи приостанавливаем выплату этой группе, входящие события для начислений сохраняем в надежной очереди. Проверяем баланс по реестру и отсутствие повторных выплат |
| Analytics | История, витрины, контрольные позиции загрузки | Существующий ClickHouse сохраняется. Отсутствующая история загружается порциями. События подключаются с зафиксированных позиций, пересечение истории и потока дедуплицируется. Отчеты сверяются до отключения SQL-доступа к монолиту |
| Booking | Поездки, принятые цены, состояние процесса, профили пассажиров и корпоративные настройки | Новые поездки идут в сервис, активные старые завершаются в монолите. История доступна через единый API с маршрутизацией к владельцу. Проверяем статусы и связи с резервами, платежами и корпоративными счетами |

При переносе Payouts фиксируем границу между загруженным реестром начислений и событиями поездок и платежей. Сохраняем бизнес-ключи начислений и обработанных операций, чтобы повтор истории не увеличил баланс. После переключения события Payments и оставшихся модулей монолита поступают только текущему владельцу счета водителя. Сверка выполняется по выгрузкам и API, без прямого доступа Payouts к БД Payments.

Учетные записи переносятся в IAM с сохранением связей с доменными профилями. Совместимые хеши импортируются, при несовместимости используется контролируемая смена пароля или миграция при входе.

Холодную историю переносим отдельно от активных данных, но сохраняем ее доступность через прежний API.

### Откат

| Момент | Действие |
| --- | --- |
| До передачи записи | Отключить новый сервис в проверочном режиме, оставить монолит владельцем. Исправить перенос и повторить сверку |
| После передачи записи | Предпочтительно откатить версию сервиса без смены владельца БД. Для возврата в монолит остановить запись группы, перенести новые изменения обратно, сверить состояния и только затем переключить владельца |
| При разделении старых и новых процессов | Остановить расширение пилота. Уже созданные сущности завершаются у своего владельца. Возврат их обработки требует отдельной передачи состояния |

Для денежных операций перед откатом выясняем неопределенные результаты у провайдера. Перенос записи не повторяет внешний платеж или выплату. Возможность обратного преобразования данных проверяется до переключения, старую схему сохраняем до завершения окна отката.

## Альтернативы и компромиссы

Перенос с полной остановкой проще, но простой зависит от всего объема БД. Независимая запись сразу в две БД неатомарна и создает расхождения. Выбран снимок с CDC и единственным владельцем записи. Цена решения - временные копии, дополнительная нагрузка и необходимость контролировать WAL, задержку репликации и корректность преобразований.
