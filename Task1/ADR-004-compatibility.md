# ADR-004. Обратная совместимость

## Контекст

Мобильные приложения нельзя обновить одновременно. Корпоративный портал, админ-панель и оставшиеся модули монолита должны продолжать работать при выделении сервисов.

## Требования

Сохранить внешние контракты, постепенно переключать обработку и не допустить одновременной записи одной сущности двумя реализациями.

## Решение

| Механизм | Применение |
| --- | --- |
| API Gateway | Сохраняет публичный адрес и маршруты, направляет запрос к текущему владельцу функции. Развертывается в нескольких экземплярах |
| Legacy API Adapter | Отдельное приложение сохраняет старые форматы запросов, ответов и ошибок при обращении к новым сервисам. Не содержит доменных правил и не владеет бизнес-данными |
| Адаптеры внутри монолита | Заменяют вызовы выделенного модуля и обращения к его таблицам на API сервиса |
| Версионирование | Совместимые изменения добавляются без удаления старых полей. Несовместимые выпускаются отдельной версией. Старая версия API не привязана к монолиту |
| Контрактные тесты | Проверяют прежние ответы, ошибки, права доступа и идемпотентность. Проверка совместимости блокирует несовместимый релиз |
| Управляемое переключение | Сначала сравнение результатов старой и новой реализации без влияния на пользователей, затем пилотная группа и постепенное расширение. Маршрут записи закреплен за сущностью или мигрируемой группой, а не выбирается случайно на каждый запрос |
| Совместимость событий | Сохраняем семантику и идентификаторы событий. Новые поля необязательны для старых потребителей. Ломающие изменения получают новую версию |

Существующие задачи Celery продолжают работать через RabbitMQ до переноса соответствующего обработчика. После передачи функции старый обработчик отключается, ожидающие задания передаются с сохранением идентификаторов. Kafka используется для доменных событий, а не как прямая замена исполнителя Celery.

Асинхронная обработка внутри сервисов не меняет смысл публичного ответа. Если прежний контракт требует результат операции, адаптер ожидает соответствующее состояние в пределах прежнего таймаута, а не возвращает прием заявки вместо результата. При неизвестном исходе действуют прежние правила проверки статуса и идемпотентного повтора. Новый асинхронный контракт вводится отдельной версией API.

Новые HTTP API и Legacy API Adapter реализуются на Python/FastAPI. Адаптер сохраняет прежние форматы ошибок и ответов, включая ошибки проверки входных данных.

Смена аутентификации выполняется отдельно от доменных переключений. На переходном этапе шлюз проверяет старые сессии через существующий механизм и новые токены через IAM. Сопоставление идентификаторов сохраняется. Сервисы проверяют права пользователя, а не доверяют произвольному заголовку клиента.

Портал и админ-панель постепенно переводятся с ORM монолита на API. Адаптер направляет платежи и счета в Payments, выплаты и запросы баланса водителя в Payouts, сохраняя прежние клиентские маршруты. Поддерживаемые клиентские контракты сохраняются и после отключения монолита. Legacy API Adapter удаляется только после завершения поддержки зависимых версий клиентов.

### Безопасность переключения

- Проверочные копии запросов не списывают деньги, не резервируют водителей и не отправляют уведомления. Пользователю возвращается ответ действующей реализации.
- Активная поездка и денежная операция продолжаются у закрепленного владельца. Повторы запросов и callbacks провайдера направляются туда же.
- Таймаут не означает, что операция не выполнена. Проверяем результат по идентификатору, повторяем с прежним ключом идемпотентности.
- После записи в новую БД запрещен автоматический fallback записи в монолит. Возможен откат версии сервиса с сохранением БД либо контролируемый перенос данных обратно по [ADR-005](ADR-005-data-migration.md).

Схема механизмов: [C2 To-Be](C2-to-be.puml).

## Альтернативы и компромиссы

Прямое переключение клиентов требует согласованного обновления приложений. Выбран общий адаптер старого API, ценой дополнительного сетевого перехода и временной поддержки двух реализаций.
