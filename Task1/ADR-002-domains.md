# ADR-002. Доменные границы

## Контекст

В компании восемь продуктовых команд, а в исходной архитектуре девять доменных модулей. Payments и Payouts обслуживают разные денежные потоки.

## Требования

Выделить сервисы по продуктовым доменам, назначить владельцев и исключить прямой доступ к чужим данным. Сохранить выплаты водителям и корпоративные сценарии.

## Решение

| Сервис и команда | Ответственность | Собственные данные и хранилища |
| --- | --- | --- |
| Booking | Жизненный цикл поездки, координация подбора водителя, история и корпоративные заказы | PostgreSQL: поездки, состояние процесса, подтвержденная цена, ссылки на пассажира, водителя и платеж |
| Driver | Профили, смены, доступность, атомарное резервирование и освобождение водителя | PostgreSQL: водители, автомобили, смены и резервы |
| Geography | Прием координат, поиск кандидатов, маршруты, ETA, геозоны и адаптеры карт | PostgreSQL: геозоны и настройки. Elasticsearch: геоиндекс. Redis: последние координаты и кеш маршрутов |
| Pricing | Тарифы, котировки, динамическая цена по спросу и предложению | PostgreSQL: правила и котировки. Redis: текущие коэффициенты и кеш |
| Payments, команда Payments | Платежи пассажиров, возвраты, корпоративные счета и интеграции с платежными провайдерами | PostgreSQL: платежи, возвраты, счета, токены провайдеров и ключи идемпотентности |
| Payouts, команда Payments | Начисления, балансы водителей, выплаты и интеграции с банковскими API | Собственная PostgreSQL: реестр начислений, балансы, реквизиты водителей, выплаты и ключи идемпотентности |
| Notification | Push-уведомления через FCM, APNs и Huawei Push Kit | PostgreSQL: устройства, шаблоны, задания и статусы доставки |
| Fraud | Проверки поездок и платежей, правила и решения антифрода | PostgreSQL: правила, результаты проверок и необходимые проекции данных |
| Analytics | Сбор бизнес-событий, аналитические витрины, данные для ML и BI | ClickHouse: события и витрины. Существующие Spark/Flink и DataLens сохраняются |

### Границы взаимодействия

- Booking координирует умный подбор: учитывает кандидатов и ETA от Geography, спрос и доступность, допускает ограниченное ожидание подходящего водителя вместо назначения ближайшего. Driver подтверждает резерв транзакционно. Устаревший геоиндекс не дает права назначить уже занятого водителя.
- Geography владеет текущими координатами, Driver владеет доступностью. Геоиндекс получает проекцию статусов, но не заменяет проверку резерва в Driver.
- Pricing получает события спроса и предложения. Booking сохраняет принятую котировку, чтобы изменение тарифа не меняло уже согласованную цену задним числом.
- Payments и Payouts имеют собственные БД, релизы и масштабирование. Payouts получает события завершенных поездок и результатов платежей, связывает их по ID поездки и формирует начисления по правилам расчета с водителями. Возвраты отражаются корректирующими записями, а не удалением истории начислений.
- События публикуются через outbox. Payouts сохраняет результат обработки и идентификатор события одной транзакцией, исключая повторное начисление. Баланс водителя изменяет только Payouts. Сбой выплат не блокирует прием платежей.
- Fraud сохраняет обязательные проверки до разрешения рискованных действий. Фоновый анализ событий дополняет, а не подменяет эти проверки.
- Analytics и Notification получают события асинхронно. Остальные сервисы используют API для немедленного ответа и события для распространения изменений. Подробная событийная модель относится к заданию 2.
- Корпоративный портал обращается к Booking за поездками, к Payments за счетами. Админ-панель управляет выплатами через Payouts API, без доступа к его таблицам.

### Общие правила

Каждый сервис владеет своей БД и миграциями. Ссылки между доменами хранятся как идентификаторы, без межсервисных SQL-запросов и внешних ключей. Копии чужих данных обновляются событиями и не становятся вторым источником записи.

Для HTTP API новых сервисов используем Python и FastAPI. Сохраняем язык и опыт команды, получаем проверку данных запросов и описание контрактов OpenAPI.

Исходный и остаточный монолит продолжают работать на Django. Сохраняем PostgreSQL, Redis, Elasticsearch, Jenkins и текущий стек наблюдаемости. Добавляем Kubernetes для независимого развертывания и автоскейлинга, Kafka для доменных событий. RabbitMQ остается для существующих задач Celery на время перехода. Потребители Kafka, обработчики outbox и аналитические задания выполняются отдельными рабочими процессами.

API Gateway и IAM относятся к платформенной команде, а не к дополнительным продуктовым доменам. IAM хранит учетные записи и роли. Профили пассажиров и корпоративные настройки поездок закрепляем за Booking, корпоративные финансовые реквизиты и счета за Payments, банковские реквизиты водителей за Payouts.

Платформенная команда предоставляет CI/CD и наблюдаемость, инфраструктурная команда развивает контейнерную платформу, SRE проверяет надежность. Analytics работает совместно с Data-инженерами. Архитектурный комитет согласует границы и контракты.

Схема: [C2 To-Be](C2-to-be.puml).

## Альтернативы и компромиссы

- Django для новых сервисов позволил бы повторно использовать больше готового кода, ORM и административных функций. Выбран FastAPI для отдельных HTTP API с явными контрактами. Компромисс - нужно отдельно организовать доступ к БД, миграции и административные интерфейсы, а перенос правил из Django проверить тестами. Бизнес-изменение и outbox по-прежнему сохраняются одной транзакцией БД.
- Общий сервис платежей и выплат проще сопровождать одной команде, но связывает релизы, масштабирование и отказы двух денежных потоков. Выбраны отдельные Payments и Payouts. Компромисс - дополнительный сервис, задержка обмена событиями и необходимость сверять платежи с начислениями.
- Выделение подбора водителей в отдельный сервис позволило бы масштабировать его независимо, но добавило бы межсервисное взаимодействие при создании поездки. Выбрана координация в Booking, атомарный резерв в Driver и геопоиск в Geography.
- Общая БД для всех сервисов проще при переносе, но сохраняет связанность релизов и общий предел масштабирования. Как целевое решение не используется.
