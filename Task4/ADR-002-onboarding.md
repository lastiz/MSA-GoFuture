# ADR-002. Подключение и мониторинг партнеров

## Контекст и требования

Подключение партнера должно быть повторяемым и не открывать доступ к частично подготовленному окружению. Требуется видеть состояние подключения, ошибки, нагрузку и соблюдение квот каждого партнера.

## Решение

Добавляется Tenant Management с HTTP API на Python/FastAPI и собственной PostgreSQL БД. Сервис хранит реестр партнеров, разрешенные регионы, общие настройки, статус и результаты шагов подключения. Фоновый обработчик относится к сервису, но запускается отдельным рабочим процессом и продолжает сохраненные в БД задания после перезапуска. Доступ к управлению инфраструктурой ограничен необходимыми операциями.

Платформенная команда отвечает за Tenant Management. Для каждого партнера назначается домашний логический регион, где изменяются его реестр, конфигурация и IAM. Каждый региональный экземпляр хранит свою часть реестра в отдельной БД, а другие регионы используют примененные копии конфигурации. Региональные БД Tenant Management и IAM имеют синхронный резерв по зонам и асинхронный резерв на разрешенной парной площадке по заданию 3. После failover запись открывается только новому владельцу. Вход и изменения realm направляются к владельцу IAM, проверка действующего токена выполняется локально.

### Подключение

| Шаг | Действие | Результат |
| --- | --- | --- |
| 1. Заявка | Оператор задает партнера, регион, квоты и параметры SSO. Проверяются договор и допустимость хранения и репликации данных | Выдан постоянный tenant_id, заявка принята |
| 2. Ресурсы | Обработчик создает БД партнеров в доменах, учетные данные, индексы, аналитические подключения и секреты. Применяет миграции через средства развертывания | Ресурсы подготовлены, внешний доступ закрыт |
| 3. IAM | Через Keycloak Admin API создаются realm, роли, клиенты, связь с IdP и приглашение администратора | Аутентификация настроена |
| 4. Конфигурация | Через API доменов применяются тарифы, разрешенные интеграции и функции. На Gateway задаются квоты | Сервисы подтвердили конфигурацию |
| 5. Проверка | Проверяются SSO, роли, доступ к своим данным и отказ в доступе к чужим. Выполняется тестовый сценарий без реальных списаний | Проверки пройдены, результат сохранен |
| 6. Активация | Tenant Management фиксирует активный статус и разрешает доступ на Gateway | Партнер получает доступ и уведомление |

Каждый шаг сохраняет результат и повторяется с тем же идентификатором заявки. Повтор не создает новый realm или БД. При ошибке партнер остается неактивным, обработчик повторяет шаг либо передает проблему оператору. Подготовленные ресурсы удаляются только по отмененной заявке после проверки, что партнер не был активирован.

Сбой Tenant Management не останавливает работающих партнеров: сервисы и Gateway используют примененную конфигурацию. Новые подключения и изменения настроек приостанавливаются. Отключение партнера блокирует новые заявки, но оставляет контролируемое завершение активных поездок и денежных операций.

### Мониторинг

Используются инструменты [задания 2](../Task2/ADR-004-monitoring.md), без отдельного стека на партнера.

| Область | Показатели и реакция |
| --- | --- |
| Подключение | Статус, длительность шагов, ошибки и повторы. Алерт оператору при остановке процесса |
| Качество сервиса | Частота ошибок, задержка запросов и доля успешных заказов по партнеру и региону |
| Ресурсы | Запросы относительно квоты, отказы по лимиту, число задач и соединений с БД. Ограничение нагрузки одного партнера не должно вытеснять остальных |
| События | Общий lag Kafka по группам, возраст необработанных задач и ошибки обработки с контекстом партнера. Общий lag топика не считается индивидуальной метрикой партнера |
| Доступ | Отказы авторизации, попытки доступа к чужим объектам, изменения ролей и SSO. Подозрительные действия передаются оператору безопасности |

Prometheus собирает технические метрики. Tenant Management публикует состояние подключения. Для небольшого согласованного набора агрегатов допускается метка партнера с контролем числа временных рядов. Идентификаторы пользователей, поездок и событий не используются как метки. Детализация по партнеру доступна в Loki и Jaeger с учетом правил доступа и маскирования данных.

Grafana и Alertmanager используются операторами платформы. Партнер видит только разрешенные агрегаты через портал: сервер проверяет роль и tenant, затем обращается к разрешенным метрикам. Прямой доступ партнеров к общим Prometheus, Loki и Jaeger закрыт. Фильтр на дашборде сам по себе не считается изоляцией.

Схема компонентов и шагов: [C2 мультитенантной платформы](C2-multitenancy.puml). Роли и границы доступа: [ADR-001](ADR-001-multitenancy.md).

## Альтернативы и компромиссы

Ручное подключение быстрее для первого партнера, но приводит к различиям конфигурации и ошибкам доступа. Полный стек мониторинга на партнера дороже в сопровождении. Выбраны автоматизированные шаги и общий мониторинг с серверной проверкой доступа, ценой поддержки Tenant Management и контроля кардинальности метрик.
