# ADR-003. Геомаршрутизация

## Контекст и требования

Новые запросы должны попадать в ближайший работоспособный и допустимый регион. Активная поездка не должна менять владельца только из-за смены сети или местоположения пользователя.

## Решение

Используем глобальный HTTPS-балансировщик с проверками доступности. Он направляет запрос к здоровому региональному Gateway, который учитывает размещение данных и владельца операции.

| Запрос | Маршрутизация |
| --- | --- |
| Новая поездка | Из разрешенных для страны и партнера регионов выбирается ближайший работоспособный, с учетом места посадки и измеренной задержки |
| Активная поездка или платеж | По ID операции и сохраненному логическому региону к текущему владельцу, даже если пользователь переместился |
| Профиль и вход | К разрешенному владельцу учетной записи. Проверка действующего токена возможна локально |
| Отказ региона | На парную площадку только после передачи владения и готовности данных. Сам health check не разрешает новую запись |

Адрес API сохраняется. Повтор запроса использует тот же логический регион и ключ идемпотентности. Балансировщик и Gateway резервируются. При отказе региона маршрут меняется только после готовности данных и блокировки записи старого владельца по [плану failover](ADR-004-failover.md).

Проверки доступности охватывают Gateway, критические API, БД и Kafka, а не только сетевой адрес.

Схема: [геомаршрутизация](geo-routing.puml). Реплики БД и Kafka на ней опущены, они показаны отдельно.

## Альтернативы и компромиссы

Только GeoDNS не учитывает владельца операции и зависит от кешей DNS. Выбран балансировщик с прикладной маршрутизацией. Для активной поездки согласованность данных важнее выбора ближайшего региона.
