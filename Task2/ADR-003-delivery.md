# ADR-003. Надежная доставка

## Контекст

Событие может потеряться между записью в БД и публикацией, а повтор доставки способен вызвать повторное начисление. Kafka сама по себе не делает внешние платежи и записи PostgreSQL одной транзакцией.

## Требования

Не терять подтвержденные изменения при обычных сбоях процессов и узлов. Обеспечить повторную доставку, безопасную обработку дубликатов и восстановление после ошибок. Отделить гарантии Kafka от гарантий внешних провайдеров.

## Решение

| Участок | Механизм |
| --- | --- |
| Транзакционные сервисы и монолит | Бизнес-изменение и сообщение outbox записываются одной транзакцией PostgreSQL. Фоновый обработчик читает неопубликованные записи, отправляет JSON в Kafka и отмечает отправку только после подтверждения брокера |
| Kafka | Replication factor 3, min.insync.replicas 2, acks all, идемпотентный producer, запрет unclean leader election. Реплики размещаются в разных зонах. При нехватке подтверждающих реплик запись не подтверждается |
| Обработчик в PostgreSQL | До обработки проверяются schema_version, region_id и tenant_id. Результат, запись обработанного event_id или command_id и следующий outbox фиксируются одной транзакцией. Offset подтверждается после фиксации. Автоматическое подтверждение отключено |
| Денежные операции | Стабильный operation_id, уникальный бизнес-ключ и идемпотентный вызов провайдера. Намерение сохраняется до вызова, результат после. При сбое между ними выполняется проверка статуса, а не повтор с новым ключом |
| Flink | Состояние восстанавливается из checkpoints в объектном хранилище. Запись результатов в Kafka транзакционная, потребители читают только подтвержденные транзакции |
| Уведомления и аналитика | Защита от повторов по ID события. Для ClickHouse используется дедупликация при загрузке и чтении витрин. Отправка push может задвоиться при потере ответа провайдера без поддержки идемпотентности |

Доставка - at-least-once: сообщения могут повторяться. Однократность денежного эффекта обеспечивают идемпотентность и проверка статуса у провайдера, а не одна Kafka.

### Публикация из outbox

При недоступности Kafka записи остаются в outbox. После сбоя обработчик продолжает отправку с прежними ID. Подтвержденная Kafka публикация может повториться, если отметка в БД не сохранилась. Для одной сущности отправка последовательная, с одним активным отправителем.

На C2 обработчики outbox включены в сервисы.

### Координаты и порядок

Geography подтверждает прием координат после записи в Kafka. Устройство повторяет неподтвержденные сообщения с прежними ID. Redis и геоиндекс обновляются из этого потока, устаревшие координаты не заменяют новые.

Порядок одной сущности определяется ее версией, для координат - сеансом и последовательностью сообщений. Между топиками общего порядка нет. Непрерывность версий проверяется для полного потока изменений. При выборочной подписке разрыв версии сам по себе не означает потерю. Ответы Saga проверяются по шагу и command_id.

### Повторы и ошибки

Временные ошибки повторяются с увеличивающейся задержкой, которой управляет приложение. Для Notification и аналитики используются retry-топики. Необрабатываемые сообщения сохраняются в региональной DLQ с причиной ошибки и алертом. Исходный offset подтверждается после надежного сохранения сообщения.

Для финансовых команд и Saga нельзя продолжать действия над той же сущностью, пропустив ошибку. Обработка приостанавливается до восстановления. DLQ не означает успешного завершения операции или отказа от компенсации.

Повтор из DLQ выполняется после исправления причины с исходными ID, регионом и партнером. Ключи дедупликации хранятся не меньше разрешенного периода повторной обработки, денежные ключи - на срок хранения операций.

### Восстановление

Outbox очищается после подтвержденной публикации и контрольного периода. Kafka позволяет повторное чтение в пределах срока хранения, более старая история восстанавливается из БД или архива. Проверяются сбои публикации, обработки и внешнего платежа с потерянным ответом.

## Альтернативы и компромиссы

Публикация после обычного коммита без outbox оставляет окно потери события. Общая распределенная транзакция не охватывает банковские API и связывает доступность доменов. Outbox, таблица обработанных сообщений и сверка добавляют хранение и эксплуатацию, но дают восстанавливаемый процесс без общей БД.
