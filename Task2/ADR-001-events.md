# ADR-001. События и потоковая обработка

## Контекст

GoFuture должна обрабатывать более 500 000 конкурентных поездок, рассчитывать динамическую цену и учитывать распределение водителей. Сохраняем девять доменов из [задания 1](../Task1/ADR-002-domains.md). Координатами владеет Geography, доступностью Driver, ценой Pricing, подбором Booking.

## Требования

Определить доменные события, региональные топики Kafka, партиционирование и потребителей реального времени. Не смешивать бизнес-события с техническими изменениями таблиц при миграции.

## Решение

### Контракт события

События передаются в JSON с семью общими полями:

| Поле | Назначение |
| --- | --- |
| event_id | Уникальный ID для исключения повторной обработки |
| event_type | Тип события, например BookingCreated |
| schema_version | Версия JSON-контракта этого типа события |
| occurred_at | Время события для потоковой обработки и измерения задержки |
| region_id | Логический регион данных, сохраняется при повторной обработке, переносе в DLQ и failover |
| tenant_id | Партнер, для изоляции данных и формирования ключа Kafka |
| payload | Данные конкретного события |

Логический регион сверяется с принадлежностью исходного или зеркального топика, а не с физической площадкой потребителя. Партнер определяется по проверенному контексту операции. В payload передаются бизнес-идентификаторы и необходимые данные. Версия состояния сущности используется для порядка изменений и не равна версии JSON-контракта. Контекст трассировки передается в заголовках Kafka. Карточные данные не передаются.

Событие описывает факт, команда запрашивает действие. В конверте команды вместо event_id и event_type используются command_id и command_type. В payload находятся saga_id, срок действия и параметры, для денежных операций также operation_id. Ответ содержит command_id и saga_id для связи с процессом.

JSON-контракты проверяются тестами в CI. Совместимые изменения добавляют необязательные поля, несовместимые требуют новой версии контракта и согласованного обновления потребителей.

| Издатель | Основные события | Потребители |
| --- | --- | --- |
| Booking | BookingCreated, BookingConfirmed, BookingCancelled, RideStarted, RideCompleted | Flink, Notification, Analytics, Fraud, Payouts |
| Driver | DriverAvailabilityChanged, DriverReserved, DriverReservationFailed, DriverReleased | Booking, Geography, Flink, Analytics |
| Geography | DriverLocationUpdated | Geography для обновления индекса, Flink, Analytics |
| Pricing | PriceQuoted, SurgeUpdated | Analytics. Booking получает котировку синхронно через API |
| Fraud | FraudCheckPassed, FraudCheckRejected | Booking, Analytics |
| Payments | PaymentAuthorized, PaymentAuthorizationFailed, PaymentAuthorizationVoided, PaymentCaptured, PaymentCaptureFailed, PaymentRefunded, CorporatePaymentCommitted | Booking, Payouts, Fraud, Notification, Analytics |
| Payouts | PayoutAccrued, PayoutAdjusted, PayoutCompleted, PayoutFailed | Notification, Analytics |
| Flink | ZoneSupplyDemandUpdated, DispatchRecommendationUpdated | Pricing, Booking, Analytics |

Ошибки компенсаций: DriverReleaseFailed и PaymentVoidFailed. Временный сбой отличается от окончательного отказа и не доказывает, что денежная операция не выполнена.

### Топики и партиционирование

Шаблон имени: регион.домен.events, для команд регион.домен.commands. Префикс обозначает логический регион данных, первоначально закрепленный за конкретной площадкой, не континент. На каждой площадке свой Kafka-кластер. При failover парная площадка обслуживает перенесенный регион, не меняя принадлежность его данных. Имя топика само по себе не обеспечивает локализацию данных.

| Топик внутри региона | Ключ партиции | Назначение |
| --- | --- | --- |
| booking.events | tenant_id + booking_id | Жизненный цикл поездки, все типы событий одной поездки в одном топике |
| driver.events | tenant_id + driver_id | Статусы, резервы и освобождение водителей |
| geography.locations | tenant_id + driver_id | Высокочастотный поток координат отдельно от транзакционных событий |
| pricing.events | tenant_id + тип сущности + ее ID | Котировки по quote_id, коэффициенты по zone_id |
| fraud.events | tenant_id + check_id | Результаты проверок |
| payments.events | tenant_id + payment_id | Авторизация, списание и возврат одного платежа |
| payouts.events | tenant_id + driver_account_id | Начисления, корректировки и выплаты по счету водителя |
| zone.signals | tenant_id + zone_id | Спрос, предложение и рекомендации Flink |
| driver.commands | tenant_id + driver_id | Резервирование и освобождение |
| payments.commands | tenant_id + payment_id | Авторизация, списание, отмена авторизации и согласование постоплаты |
| fraud.commands | tenant_id + check_id | Проверка поездки |

Ключ объединяет tenant_id и ID сущности. Это распределяет нагрузку внутри региона и сохраняет порядок одной сущности в партиции. У независимых потребителей отдельные consumer groups. Между топиками общего порядка нет, ответы Saga сопоставляются по saga_id и command_id. Число партиций и срок хранения подбираются нагрузочными тестами.

На [C2](C2-event-platform.puml) показаны ключевые сообщения. Каждый потребитель выбирает нужные типы событий своего домена. Надежная публикация описана в [ADR-003](ADR-003-delivery.md).

### Flink

Flink объединяет события поездок, доступности и координат по региону, партнеру и зоне. Спрос определяется ожидающими заказами, предложение - уникальными доступными водителями. Повторные сообщения не увеличивают счетчики. Учитываются время события, опоздания и устаревание координат.

Результат: ZoneSupplyDemandUpdated для Pricing и DispatchRecommendationUpdated для Booking. Pricing применяет правила динамической цены и публикует SurgeUpdated, Booking учитывает рекомендации при подборе. Резерв подтверждает только Driver. При устаревших сигналах используются базовый тариф и подбор по актуальной доступности.

## Альтернативы и компромиссы

Выбран Flink: уже есть в стеке, поддерживает объединение потоков и обработку по времени события. Альтернатива - Kafka Streams, но использование существующего Flink позволяет сохранить единый инструмент потоковой обработки. Простые команды и уведомления обрабатывают Python-потребители. Компромисс - хранение состояния Flink и задержка обновления межсервисных данных.
